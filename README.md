# Ядро магазина цифровых товаров

Бэкенд площадки цифровых товаров: каталог, заказы, приём оплаты по вебхуку,
автоматическая выдача ключей через поставщиков, сверка и восстановление.

Первый этап построен вокруг трёх вещей, которые задание называет главными:
однократная выдача, корректная обработка таймаута и восстановление после сбоя.

Второй этап добавляет поверх этого четыре задачи, и все четыре сделаны:

1. **Заказ из нескольких товаров, где часть может не выдаться.** Единицей выдачи
   стала позиция заказа: выданное остаётся у покупателя, за невыданное деньги
   возвращаются, и `оплачено = выдано + возвращено` при любом сбое и повторе.
2. **Поставщик, которому нельзя доверять.** Ответ поставщика проверяется, а не
   принимается на веру: дубль чужого кода и код от другого товара отбраковываются,
   один код никогда не уходит двум покупателям, расхождения разбираются сами.
3. **Всплеск заказов и лимит поставщика** (бонус). Лимит считается по запросам и
   не превышается, лишнее ждёт, ожидание не стоит задаче ни одной попытки,
   оплаченное обслуживается раньше неоплаченного, прогресс виден.
4. **Восстановление картины на любой момент** (бонус). История только
   дополняется — это обеспечено триггером, а не соглашением, — и состояние заказа
   и денег на прошлую дату восстанавливается по ней.

**Ответы на вопросы из формата сдачи — в [docs/ANSWERS.md](docs/ANSWERS.md):**
как воспроизвести частичный сбой и поведение недобросовестного поставщика, как
проверить, что деньги сходятся, затраченное время и готовность внести правку на
звонке.

Стек: Node.js 22, TypeScript, Fastify, PostgreSQL 16, без ORM и без внешнего
брокера очередей.

## Быстрый старт

### Через docker compose

```bash
docker compose up --build
```

Поднимутся Postgres, API на порту 3000, воркер (метрики на 3001) и две заглушки
поставщиков на портах 4001 и 4002. Миграции и сидирование выполняются
автоматически: сервис `migrate` отрабатывает один раз и завершается, остальные
ждут его успеха и не стартуют против наполовину применённой схемы.

Наружу на всех интерфейсах слушает только API. Postgres, метрики воркера и
заглушки привязаны к `127.0.0.1`: они часть стенда, а не публичная поверхность.

Образ один на все пять ролей — процесс выбирается командой, поэтому API, воркер,
миграции и заглушки не могут разъехаться между собой. TypeScript компилируется на
этапе сборки, в рантайме остаются только `node` и production-зависимости: ни
`tsx`, ни `typescript` в финальный образ не попадают. Процессы работают не от
root, с read-only корневой файловой системой, а `tini` доводит `SIGTERM` до
приложения, так что штатное завершение действительно отрабатывает.

Переопределяемые переменные (через `.env` в корне или окружение):
`ADMIN_TOKEN`, `LOG_LEVEL`, `POSTGRES_USER`, `POSTGRES_PASSWORD`, `POSTGRES_DB`
и хостовые порты `API_HOST_PORT`, `WORKER_METRICS_HOST_PORT`,
`SUPPLIER_A_HOST_PORT`, `SUPPLIER_B_HOST_PORT`, `POSTGRES_HOST_PORT`.
`DATABASE_URL` намеренно не переопределяется: в `.env.example` он указывает на
`127.0.0.1` для запуска без docker, и внутри контейнеров это увело бы всех на
хост вместо сервиса `postgres`.

Логи в контейнерах — структурированный JSON. `LOG_PRETTY` работает только в
режиме без docker: `pino-pretty` это dev-зависимость, и в production-образе её
нет намеренно.

Симулятор оплаты внутри стенда запускается из того же образа. Скрипты `npm run`
собраны вокруг `tsx` и в образе недоступны, поэтому вызывается скомпилированный
файл:

```bash
docker compose run --rm --no-deps -e API_URL=http://api:3000 api \
  node dist/src/stubs/payment-simulator/cli.js race --order "$ORDER" --amount 1990 --concurrency 50
```

Вспомогательные скрипты из `scripts/` (`npm run dev`, `bench:catalog`) в образ не
входят — это инструменты разработки, им место в локальном запуске ниже.

### Без docker

Нужен установленный PostgreSQL 16. Скрипт `scripts/pg-dev.sh` поднимает локальный
кластер в каталоге проекта, отдельно от системного.

```bash
npm ci
scripts/pg-dev.sh start
export DATABASE_URL=postgres://postgres@127.0.0.1:55432/digital_shop
npm run migrate
npm run seed
npm run dev
```

`npm run dev` запускает все четыре процесса в одном терминале.

Тестам нужен доступный Postgres и переменная `DATABASE_URL` либо

## Как воспроизвести проверку гонок

Команды `npm run simulate` ниже относятся к запуску без docker. Если стенд поднят
через compose, `node_modules` на хосте нет — тот же сценарий запускается из
образа, подменой одной команды:

```bash
npm run simulate -- <args>   # без docker

docker compose run --rm --no-deps -e API_URL=http://api:3000 api \
  node dist/src/stubs/payment-simulator/cli.js <args>   # через compose
```

Создаём заказ, затем стреляем по нему пятьюдесятью одновременными вебхуками.

```bash
ORDER=$(curl -s -X POST http://127.0.0.1:3000/orders \
  -H 'content-type: application/json' -d '{"sku":"KEY-GTA5"}' | jq -r .order_id)

# 50 параллельных вебхуков с РАЗНЫМИ event_id (критерий 1)
npm run simulate -- race --order "$ORDER" --amount 1990 --concurrency 50

curl -s "http://127.0.0.1:3000/orders/$ORDER" | jq
```

Ожидаемо: один вебхук отвечает `applied`, остальные сорок девять `ignored`,
заказ в статусе `delivered`, код ровно один.

```bash
# 50 повторов ОДНОГО event_id (критерий 2)
npm run simulate -- replay --order "$ORDER" --amount 1990 --concurrency 50
```

Ожидаемо: сорок девять ответов `duplicate` и один `ignored`, состояние заказа не
меняется. `ignored`, а не `applied`, потому что этот заказ уже доведён до
`delivered` предыдущей командой: событие проходит дедупликацию по `event_id`, но
финальный заказ не трогает. Если запустить `replay` по свежему оплаченному
заказу, первый ответ будет `applied`.

Проверить в базе, что выдача ровно одна:

```sql
SELECT count(*) FROM deliveries WHERE order_id = '<ORDER>';   -- 1
SELECT count(*) FROM payment_events WHERE order_id = '<ORDER>'; -- 50 или 1
```

### Вебхук раньше заказа (критерий 3)

```bash
npm run simulate -- early --amount 890
# скрипт печатает order_id, который он использовал
curl -s -X POST http://127.0.0.1:3000/orders -H 'content-type: application/json' \
  -d '{"sku":"GIFT-ROBLOX-800","order_id":"<напечатанный order_id>"}'
```

Вебхук по несуществующему заказу получает `200` и паркуется. При создании заказа
с тем же id он применяется, и заказ доходит до `delivered`.

## Как воспроизвести отказ и фолбэк поставщика

Заглушки принимают настройку хаоса на лету.

### Ловушка таймаута (критерий 4)

Поставщик A выдаёт код и не отдаёт ответ. Это ровно тот случай, ради которого всё
и строилось: таймаут не равен отказу.

```bash
curl -s -X POST http://127.0.0.1:4001/admin/chaos -H 'content-type: application/json' \
  -d '{"forced_outcome":"timeout","hang_ms":3000,"issue_before_hang":true}'

ORDER=$(curl -s -X POST http://127.0.0.1:3000/orders \
  -H 'content-type: application/json' -d '{"sku":"KEY-EFT"}' | jq -r .order_id)
npm run simulate -- pay --order "$ORDER" --amount 3490

sleep 8
curl -s "http://127.0.0.1:3000/orders/$ORDER" | jq
curl -s "http://127.0.0.1:4001/admin/issuances?order_id=$ORDER" | jq
```

Ожидаемо: первая попытка в журнале помечена как `timeout`, вторая идёт с тем же
`request_id` и получает тот же самый код, у поставщика ровно одна выдача, у нас
ровно одна строка в `deliveries`.

Сценарии этого раздела написаны для первого этапа и продолжают работать без
правок: форма `{"sku": …}` создаёт корзину из одной позиции, а `deliveries` и
`supplier_stub.issuances` по-прежнему хранят `order_id`. Изменился вид
идентификатора запроса — теперь это `req_<позиция>-<поставщик>-<эпоха>`, — но
правило то же: на таймаут эпоха не растёт, поэтому повтор приходит к поставщику
с тем же идентификатором и получает тот же код.

### Фолбэк на резервного поставщика (критерий 5)

```bash
curl -s -X POST http://127.0.0.1:4001/admin/chaos -H 'content-type: application/json' \
  -d '{"forced_outcome":"error"}'
ORDER=$(curl -s -X POST http://127.0.0.1:3000/orders \
  -H 'content-type: application/json' -d '{"sku":"KEY-CS2-PRIME"}' | jq -r .order_id)
npm run simulate -- pay --order "$ORDER" --amount 1290
sleep 4
curl -s "http://127.0.0.1:3000/orders/$ORDER" | jq '.delivery.supplier'   # supplier_b
```

Вернуть поставщика в норму: `-d '{"forced_outcome":null}'`.

### Пустой остаток и восстановление (критерий 6)

SKU `SUB-SPOTIFY-1M` намеренно засеян без ключей у обоих поставщиков, поэтому
сценарий воспроизводится сразу после `npm run seed`.

```bash
ORDER=$(curl -s -X POST http://127.0.0.1:3000/orders \
  -H 'content-type: application/json' -d '{"sku":"SUB-SPOTIFY-1M"}' | jq -r .order_id)
npm run simulate -- pay --order "$ORDER" --amount 299
sleep 3
curl -s "http://127.0.0.1:3000/orders/$ORDER" | jq -r .status   # out_of_stock

curl -s -X POST http://127.0.0.1:3000/admin/inventory/replenish \
  -H 'authorization: Bearer dev-admin-token' -H 'content-type: application/json' \
  -d '{"sku":"SUB-SPOTIFY-1M","count":5}'

curl -s -X POST "http://127.0.0.1:3000/admin/orders/$ORDER/redeliver" \
  -H 'authorization: Bearer dev-admin-token'
sleep 3
curl -s "http://127.0.0.1:3000/orders/$ORDER" | jq -r .status   # delivered
```

Восстановление здесь показано двумя путями, и `redeliver` нужен только чтобы не
ждать.

`replenish` пополняет пул у поставщика и обновляет счётчики витрины, но заказ он
не толкает: заказ доводит фоновая свёртка, а она по построению берёт только те,
что не двигались дольше `STUCK_ORDER_AFTER_MS` (по умолчанию 30 секунд). Свежий
`out_of_stock` под это условие не подходит — иначе свёртка конкурировала бы с
воркером, который прямо сейчас этот заказ обрабатывает. Поэтому в ответе
`replenish` честно стоит `"recovered":{"ordersRequeued":0}`.

Если после пополнения ничего не делать и подождать, заказ дойдёт до `delivered`
сам примерно за 35 секунд: 30 на порог «зависшего» плюс интервал сканирования
`RECOVERY_SCAN_INTERVAL_MS`. `redeliver` ставит задачу в очередь безусловно и
сокращает это до секунды. Оба пути идут через одну и ту же выдачу с теми же
производными `request_id`, поэтому задвоения не будет ни в одном из них.

## Как воспроизвести сценарии второго этапа

Подробные пошаговые сценарии с фактическим выводом — в
[docs/ANSWERS.md](docs/ANSWERS.md). Кратко:

```bash
ADMIN='authorization: Bearer dev-admin-token'

# 1. Частичный сбой: SUB-SPOTIFY-1M засеян пустым у обоих поставщиков
curl -s -X POST localhost:3000/orders -H 'content-type: application/json' -d '{
  "items":[{"sku":"KEY-CS2-PRIME"},{"sku":"STEAM-TOPUP-500"},{"sku":"SUB-SPOTIFY-1M"}]}'
npm run simulate -- pay --order ord_... --amount 2089
curl -s localhost:3000/orders/ord_...
# status: partially_delivered, money: paid 2089 = delivered 1790 + refunded 299

# 2. Недобросовестный поставщик
curl -s -X POST localhost:4001/admin/chaos -H 'content-type: application/json'      -d '{"forced_outcome":"duplicate_code"}'      # или foreign_code, error_after_issue
# ... заказ и оплата ...
curl -s -H "$ADMIN" localhost:3000/admin/quarantined-codes

# 3. Деньги сходятся
curl -s -H "$ADMIN" localhost:3000/admin/money            # из товаров
curl -s -H "$ADMIN" localhost:3000/admin/ledger/balance   # из журнала
curl -s -H "$ADMIN" localhost:3000/admin/reconciliation   # 200 = здоров

# 4. Лимит поставщика и очередь
docker exec -it digital-shop-postgres-1 psql -U postgres -d digital_shop -c   "UPDATE supplier_rate_limits SET capacity=4, refill_per_minute=60, tokens=4, updated_at=now()"
curl -s -H "$ADMIN" localhost:3000/admin/queue/progress

# 5. Состояние на прошлый момент
curl -s -H "$ADMIN" "localhost:3000/admin/orders/ord_.../at?ts=2026-09-09T12:59:03Z"
```

Уменьшать `STUCK_ORDER_AFTER_MS` до секунды при ручной проверке удобно: по
умолчанию свёртка считает позицию застрявшей через 30 секунд, и демонстрация
частичного сбоя занимала бы лишнюю минуту.

## API

Спецификация OpenAPI 3.0 лежит в [docs/openapi.yaml](docs/openapi.yaml): все
методы ниже с параметрами, телами, кодами ответов и формами ошибок. Чтобы
посмотреть её отрисованной, вставьте
[raw-ссылку](https://raw.githubusercontent.com/alexei-drazdoff/core-digital-shop-backend/main/docs/openapi.yaml)
в [editor.swagger.io](https://editor.swagger.io/).

Публичные методы.

| Метод | Путь | Что делает |
|---|---|---|
| GET | `/health`, `/ready` | проверки живости и готовности |
| GET | `/metrics` | метрики в формате Prometheus |
| GET | `/catalog/products` | витрина, фильтр `type`, keyset-пагинация через `cursor` |
| GET | `/catalog/products/:sku` | карточка товара |
| POST | `/orders` | создание заказа: `{"sku": …}` или `{"items": [{"sku": …, "qty": …}]}`, поддерживает `Idempotency-Key` |
| GET | `/orders/:id` | заказ, позиции с кодами и возвратами, сходимость денег, журнал обращений к поставщикам |
| POST | `/webhooks/payment` | вебхук оплаты по контракту из задания |

Воркер слушает отдельно, по умолчанию на порту 3001, и отдаёт там `/health` и
`/metrics`. Реестр метрик у каждого процесса свой, а счётчики выдач, повторов и
осиротевших кодов инкрементируются именно в воркере, поэтому без собственного
слушателя их было бы некуда собирать.

Административные методы, авторизация `Authorization: Bearer $ADMIN_TOKEN`.

| Метод | Путь | Что делает |
|---|---|---|
| GET | `/admin/reconciliation` | отчёт сверки, `200` если расхождений нет, `409` если есть |
| GET | `/admin/money` | сходимость денег по каждому заказу, считается из товаров, а не из журнала |
| GET | `/admin/ledger/balance` | остатки по счетам и проверка баланса |
| GET | `/admin/reports/period` | итоги за период `[from, to)` из журнала |
| GET | `/admin/orders/:id/at?ts=` | состояние заказа и денег на прошлый момент |
| GET | `/admin/orders/:id/history` | полная append-only история заказа |
| GET | `/admin/queue/progress` | глубина очереди, выдано/в ожидании, остаток квоты поставщиков |
| GET | `/admin/quarantined-codes` | коды, отбракованные у поставщика |
| POST | `/admin/orders/:id/redeliver` | повторная постановка неразрешённых позиций на выдачу |
| POST | `/admin/orders/:id/settle` | пересчёт итога заказа по позициям |
| POST | `/admin/recover` | ручной запуск подчистки зависших позиций |
| POST | `/admin/reconcile-suppliers` | разбор повисших расхождений с поставщиками |
| POST | `/admin/inventory/replenish` | пополнение пула у поставщика |
| POST | `/admin/sync-stock` | синхронизация остатков витрины |

### Создание заказа

```http
POST /orders
Idempotency-Key: 6f1c0a7e-...

{ "sku": "KEY-GTA5", "customer_ref": "user-42", "order_id": "ord_..." }
```

Или корзина из нескольких товаров:

```http
POST /orders

{ "items": [ { "sku": "KEY-GTA5" }, { "sku": "STEAM-TOPUP-500", "qty": 2 } ] }
```

Обе формы принимаются, но не одновременно: запрос, указавший и `sku`, и `items`,
не имеет очевидного смысла, и угадывать хуже, чем отказать. Каждая единица
товара становится отдельной позицией, потому что одна единица — это один код от
одного поставщика с одним `request_id`; сворачивание двух единиц в количество
сделало бы «одна из них не выдалась» невыразимым.

Поле `order_id` необязательное. Оно есть затем, чтобы платёжной стороне можно было
сообщить идентификатор до того, как строка заказа появится у нас, и именно это
делает сценарий с ранним вебхуком воспроизводимым.

При повторе с тем же `Idempotency-Key` возвращается исходный заказ и код `200`
вместо `201`, поэтому клиент отличает повтор от нового создания.

## Заглушки

Обе заглушки реализуют контракт `POST /issue` и хранят выдачи по `request_id`,
поэтому повтор с тем же идентификатором возвращает тот же код.

Сверх контракта у них есть служебные методы, они помечены как расширение:
`GET /stock` для синхронизации остатков, `GET /admin/issuances?order_id=` для
проверок, `POST /admin/replenish` для пополнения и `POST /admin/chaos` для
настройки отказов.

Параметры хаоса: `error_rate`, `timeout_rate`, `latency_ms`, `hang_ms`,
`issue_before_hang`, `hang_before_lookup` и `forced_outcome` для детерминированных
сценариев. `issue_before_hang` означает, что код будет выдан, а ответ не дойдёт,
то есть ровно ту самую ловушку. `hang_before_lookup` дополнительно моделирует
поставщика, который стал совсем недоступен уже после выдачи.

Второй этап добавил три НЕЧЕСТНЫХ режима `forced_outcome`, качественно отличных
от первых трёх: те описывают пропавший ответ, эти — пришедший ответ, за которым
ничего не стоит.

| `forced_outcome` | Что делает заглушка |
|---|---|
| `duplicate_code` | отдаёт код, уже выданный другому запросу, ничего не потратив |
| `foreign_code` | отдаёт свободный код из пула ДРУГОГО товара, честно называя его SKU |
| `error_after_issue` | тратит ключ и отвечает `503` |

Собственные ограничения заглушки не дают ей выдать один ключ дважды через
честный путь, поэтому нечестные ветки намеренно обходят её бухгалтерию — именно
так это и выглядит снаружи у настоящего поставщика.

## Каталог под нагрузкой

```bash
npm run bench:catalog
```

Скрипт создаёт временную базу, засевает пять тысяч SKU и четверть миллиона ключей,
замеряет три варианта запроса витрины и пишет планы выполнения в
[docs/EXPLAIN.md](docs/EXPLAIN.md).

## Затраченное время

### Первый этап

Около 17 часов за четыре подхода: два вечера и два утра.

| Что | Часов |
|---|---|
| Разбор задания, схема данных, продумывание гарантий однократной выдачи | 2 |
| Заказы, вебхук оплаты, автовыдача, переходы статусов | 3 |
| Exactly-once, очередь в базе как transactional outbox, тесты на гонки | 3 |
| Две заглушки, таймауты, повторы с бэкоффом, фолбэк, ловушка таймаута | 3,5 |
| Сверка, журнал денег, восстановление, логи и метрики | 2 |
| Схема каталога, индексы, бенчмарк и разбор плана | 1,5 |
| Docker, CI, README и документация | 2 |

Больше всего ушло на третий блок, и почти всё это время не на код, а на то,
чтобы аккуратно развести «поставщик отказал» и «поставщик не ответил». Второе
место — тесты на гонки: воспроизвести их детерминированно оказалось дороже, чем
написать сам механизм защиты.

### Второй этап

Около четырёх часов за один заход с перерывами. Разбивка по задачам в
[docs/ANSWERS.md](docs/ANSWERS.md), раздел 3.

## Конфигурация

Все параметры читаются из окружения и проверяются схемой при старте, процесс с
некорректной конфигурацией падает сразу. Полный список с значениями по умолчанию
лежит в `.env.example`.
